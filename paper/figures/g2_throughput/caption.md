**Figure G2 — Force-evaluation throughput, CPU vs GPU: compute-only vs end-to-end.**

Throughput (points evaluated per second, $= N/\text{wall-time}$) versus array length $N$ (number of points per call) for a vectorized Plummer $F_R$ evaluation, on numpy (CPU, one core: the elementwise evaluation does not multi-thread) and jax/torch on two GPUs: *(a)* the development box's NVIDIA TITAN Xp (a consumer card with float64 at 1/32 of its float32 rate; jax 0.10.1, torch 2.12.0) and *(b)* an NVIDIA H100 80GB on the Trillium cluster (jax 0.11.2, torch 2.14.1), each panel with numpy on that machine's own CPU. Each marker is the median over repeated calls. Colours follow the paper-wide convention: numpy black, jax blue, torch orange/red, a darker shade for the faster GPU; jax is jit-compiled (solid), torch runs eagerly (dashed). Two regimes are shown for each GPU backend:

- **Compute-only (filled markers):** the input array is resident on the GPU before timing and the result stays on-device — the timed wait (`block_until_ready` / `cuda.synchronize`) is for the kernel, not a copy-back. This is the best-case GPU throughput, with host$\leftrightarrow$GPU transfers *excluded*.
- **End-to-end ($+$transfer; dotted, hollow markers):** each call starts from a host (numpy) array and returns a host array, so it includes the host$\rightarrow$device and device$\rightarrow$host copies — the realistic cost of calling galpy on the GPU from a numpy workflow.

Dotted slope-1 lines mark constant wall-time per call (0.1, 1, 10, 100 ms); on a log–log throughput-vs-$N$ plot a fixed wall-time $t_0$ is the line $N/t_0$.

**Take-aways:**
- At small $N$ the GPU backends are **launch/overhead-bound** — wall-time per call is roughly constant, so the curves hug the $\sim$0.1–0.5 ms reference lines and throughput rises only because $N$ does. The CPU, with negligible per-call overhead, wins here.
- **Compute-only**, the GPU overtakes the CPU around $N\sim10^{4}$ on both machines. At $N=10^{7}$ the TITAN Xp is $\sim\!100\times$ faster than one core of its CPU ($\sim\!10^{9}$ vs $\sim\!10^{7}$ pts/s); the H100 reaches $\sim\!7\times10^{10}$ pts/s under jax, $\sim\!800\times$ one core of Trillium's (faster) CPU, and is still launch-bound (flat wall-time) up to $N\sim10^{6}$.
- **End-to-end**, the round-trip copy is PCIe-bandwidth-bound (cost $\propto N$ while the kernel cost is sub-linear), so it saturates GPU throughput at $\sim\!10^{8}$ pts/s on the TITAN Xp and $\sim\!4$–$8\times10^{8}$ pts/s on the H100 — **one to two orders of magnitude below compute-only** — and the curves turn over at the largest $N$. The honest GPU win for one-shot host calls is a modest $\sim\!4$–$6\times$ on either GPU (the faster H100 is paired with a faster CPU and the same PCIe bottleneck), and the CPU crossover moves to larger $N$.
- **Implication:** the GPU pays off when data *stays* on-device across many chained operations (a full differentiable pipeline — forces, orbit integration, action-angle, DF — without round-trips), not for isolated calls from a host workflow. That on-device pipeline is exactly what the multi-backend layer is built to enable.
